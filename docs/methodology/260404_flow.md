当前实际模式
按你现在的配置，config.json、config_odometry_bspline.json、config_ros.json 对应的是：
```
odometry 主体是 BSpline CT，frontend_mode=CT_LIDAR_CPU
frontend_only_mode=true
initialization_mode=NAIVE
ct_lidar_target_mode=GLOBAL_IVOX_REFERENCE
ct_lidar_bucket_mode=SINGLE_BUCKET
enable_local_mapping=false
enable_global_mapping=false
```
所以你当前真正跑到的主路径是：
```
IMU + LiDAR -> 时间校验/预处理 -> AsyncOdometry -> BSpline local CT frontend -> odometry/frame/trajectory 输出 -> 把当前帧插入 frontend target ivox
```
而不是完整的 frontend + monolithic fixed-lag + backend + local/global mapping。

# 1. 传感器数据怎么进来、怎么校验时间、怎么对齐
入口在 iap_rosnode.cpp：

IMU 到来：

取 ROS 时间戳，加 imu_time_offset
用 time_keeper.cpp validate_imu_stamp() 检查：
是否回退
是否有大 gap
是否和最近 LiDAR 时间差过大
合法后送进 async_odometry_estimation.cpp
LiDAR 到来：

从 PointCloud2 提取 raw points
TimeKeeper::process() 做两件事：
把 per-point time 统一成“相对首点的秒”
必要时把 frame stamp 改成首点时间
这里会自动处理 Livox 那种“绝对纳秒 per-point time”
然后进入 cloud_preprocessor.cpp：
下采样
距离滤波
时间排序
可选 global shutter
可选 cropbox
可选离群点移除
计算 scan_end_time
预先找每点 kNN 邻居
之后送进 AsyncOdometry
真正的 IMU/LiDAR 对齐不是“按最近帧配对”，而是：

async_odometry_estimation.cpp 会一直等到
raw_frame->scan_end_time <= last_imu_time
也就是：等这帧扫描结束之前的 IMU 都到了，才开始做这一帧 odometry
GNSS 如果启用：

GNSS extension 先把原始观测、星历、anchor 写进 shared_state.hpp
BSpline odom 在每个 segment 上按时间窗消费 consume_epochs_in_range(start,end,tolerance)
所以 GNSS 是按 segment 时间窗匹配，不是 node 层直接同步

主逻辑在 odometry_estimation_bspline.cpp 和 ct_local_frontend.cpp。

当前 frontend_only=true 时：

首帧：

走初始化
用初始 pose 建一个 control window
输出第一帧 EstimationFrame
后续每帧：

先把当前预处理点云变成 source cloud，并估计点协方差
选 frontend target

所以优先直接拿全局滚动 ct_target_ivox_
如果配置成 ACTIVE_WINDOW_SNAPSHOT，则会从窗口里的 active frames 临时拼局部 snapshot
构造一个 local spline problem
前端 local spline 的状态在 ct_local_frontend.hpp / ct_backend_summary.hpp：

4 个 pose control points
1 个 velocity state
1 个 gyro bias
1 个 accel bias
1 个 gravity
连续时间真正介入的位置是 spline_state_layout.hpp 和 spline_evaluator.cpp：

spline 用显式 knot + 4 个 control pose 表示
任意时刻 t 会先求 support_at(t, sensor)
得到这时刻对应的 4 个 control keys、span、u
再用 SplineEvaluator 在这个 t 上求：
pose
velocity
acceleration
也就是说，LiDAR 和 IMU 都不是绑在单个离散 pose 上，而是绑在同一条连续时间 spline 上的不同时间点。

3. factor 怎么建，Jacobian 怎么算
LiDAR 因子在 integrated_bspline_gicp_factor.hpp / integrated_bspline_gicp_factor.cpp：

先按 bucket 策略分桶
你当前是 SINGLE_BUCKET，所以每帧 1 个 bucket
每个 bucket 生成一个 SplineBucketContext
每个 bucket 挂一个 IntegratedSplineGICPFactor
因子依赖这 4 个 control poses
LiDAR Jacobian：

NUMERIC_FULL：
对每个 control pose 做 Expmap(delta) 扰动
重新插值得到 bucket pose
数值差分
SEMI_ANALYTIC：
平移部分直接按 spline basis 权重传播
旋转部分对“加权 quaternion blend”做链式求导
对单点残差再乘上 Mahalanobis/GICP 项
当前代码默认更偏向 SEMI_ANALYTIC
IMU 因子在 integrated_bspline_imu_factor.hpp / integrated_bspline_imu_factor.cpp：

每个 IMU sample 都在 sample stamp 上求 spline pose/vel/acc
gyro 由相邻时刻旋转差分得到
accel 由世界加速度加 gravity，再转到 body
residual 是：
gyro_pred - (gyro_meas - gyro_bias)
acc_pred - (acc_meas - acc_bias)
IMU Jacobian：

对 4 个 pose controls：数值差分
对 gyro bias / accel bias：解析块
对 gravity：解析块，底部是 R_body_world
Velocity 因子在 integrated_bspline_velocity_factor.cpp：

用 spline 平移的有限差分速度
约束到显式 velocity state
对 pose controls 仍是数值差分
GNSS 因子只在 compact backend 路径里用，定义在 integrated_bspline_gnss_factor.cpp：

pseudorange / doppler 都是 spline-native
pose 对 4 个 controls 的 Jacobian 也是数值差分
clock / ECEF anchor / ECEF rotation 的 Jacobian 用底层 GNSS model 直接给
4. 前端输出什么，滑窗怎么移动，后端和 mapping 怎么接

你当前 frontend_only=true 时：

旧的 monolithic active-window 不移动
不做 prune/marginalization

control_window_->advance(...)

为新 segment 挂：
bucketed LiDAR factors

这部分在 odometry_estimation_bspline.cpp 和 bspline_fixed_lag_registry.hpp。

compact backend 在 ct_compact_backend.cpp：

输入不是 raw LiDAR bucket factors
输入是：
frontend layout
backend_summary
当前 segment 的 GNSS epochs
GNSS anchor / noise / lever arm
它当前做的事是：
seed ECEF/clock/velocity states
把 pseudorange / doppler factors 挂进 graph
它自己不单独再跑一轮优化器
所以它更像“compact GNSS/backend factor 注入层”，不是独立 solver
local/global mapping 在当前配置里没开；如果打开：

iap_rosnode.cpp 只把 marginalized odom frames 丢给 AsyncSubMapping
sub_mapping.cpp
维护一个 submap 内部图
选 keyframe
建 between / VGICP / IMU factors
keyframe 数到阈值后跑 LM
合并成一个 SubMap
global_mapping.cpp
把 submap 当节点
建 submap-between、implicit loop、matching cost、可选 IMU endpoint 因子
用 ISAM2 增量优化
周期性或按请求找重叠和优化
